# Расчёты переходов, кубковой сетки и нейтрального финала

Приняты 2026-10-15 три внешних **вычислительных подпакета** AND-119/123/125.
Они объединены с основной кодовой базой после review и исправлений. Это чистые
Python-функции с неизменяемыми входами/результатами и явным seed: без БД,
сети, часов, Telegram и собственного worker. Игровое подключение больших задач
остаётся незавершённым; существующий внутрикомплектный rollover не заменён.

| Модуль | Публичный вход → выход | Policy |
|---|---|---|
| `domain/league_allocation.py` | `allocate(Sequence[LeagueSnapshot], seed=...) → AllocationResult` | `league-allocation-v1` |
| `domain/cup_bracket.py` | `build_bracket(season_id=..., league_set_id=..., entries=..., seed=...) → CupBracket` | `cup-bracket-v1` |
| `domain/neutral_final.py` | `settle_neutral_final(NeutralFinalSnapshot) → NeutralFinalResult` | `neutral-final-v1` |

## Переходы

Вход содержит frozen итоговый порядок десяти клубов каждой лиги, tier 1..5,
league/set/season IDs и общий cohort key. В одном комплекте должен быть один
завершённый сезон, один сезон не может принадлежать разным комплектам. Каждая
вертикаль полная; клубы и лиги не повторяются. Даты и завершение турниров
проверяет orchestration, а не произвольная строка `cohort_key`.

Две верхние/две нижние команды меняют уровень одновременно, с границами tier 1/5.
Остальные сохраняют свою лигу. Promoted/relegated pools перемешиваются отдельно
по соседним уровням: каждый получатель принимает по два клуба из каждого
применимого направления и сохраняет ровно десять. Межкомплектные маршруты допустимы.
`result.assignments` даёт source/place/destination/movement каждого клуба;
`result.draws` сохраняет проверяемые порядки вакансий и обоих пулов.

До подключения нужно сохранить входной cohort и результат в одном durable receipt,
согласовать границы завершённых сезонов, атомарно создать новые membership/сезоны,
однократно обработать возраст, пенсионные решения и спонсорство по destination tier.
Не пересчитывать draw при retry; не менять исторические membership/results.

## Кубок

`CupEntry` содержит одну лигу, tier и frozen entry order. В первом сезоне порядок
берётся из сохранённого стартового жребия; затем источник отбора фиксируется явно.
Текущая промежуточная таблица не меняет вход посреди кубка.

Сетка содержит 49 противостояний / 97 матчей. Нижние восемь tier 5 начинают
в циклах 1–2; верхние два tier 5 и tier 4 входят в 3–4; tier 1..3 — в 9–10.
Двухматчевые раунды обмениваются полем, финал один нейтральный в цикле 17.
Кубковый день 18 свободен. Это номера циклов с кубковым матчем в фазе дня 1,
а не ежедневные матчи; день 3 цикла остаётся добровольным окном.

`all_matches` раскрывает legs, `resolve_slot` разрешает известного участника,
`possible_clubs` / `possible_tie_clubs` дают условные клубы будущих слотов.
После вылета проигравший исключается из зависимых ветвей. Любой публичный reader
проверяет весь словарь результатов. Победитель противостояния принимается только
после определения обоих участников и завершения всех его предшественников.
`champion` не объявляет чемпиона на основе одной записи финала без прошлых результатов.

Полный граф также проверяется при восстановлении: все 50 frozen участников входят
в правильных раундах, нет циклов, повторного использования победителя одной пары,
пропавшего финала или неверных дней. Seeded draws и structural UUIDs исходного
агентского v1 сохранены; исправления не меняют корректные сетки.

До подключения остаются persisted draw/dependencies, окончательные tie results из
общего knockout runtime AND-124 (агрегат/ET/пенальти), десятидневная материализация
kickoff/jobs, резервирование тренировочных дат, расписание и outbox. Не трактовать
ничью отдельного матча как победителя и не назначать соперника из неопределённого слота.

## Нейтральный финал

До старта замораживаются arena ID/capacity/ticket price, два club IDs, обе фанбазы,
seed и policy. `neutral=True` и `home_advantage=0` передаются явно потребителю.
Вычисляется `min(capacity, (fans_a + fans_b) * 8000 // 10000)` зрителей и целая
выручка. **8000 — исходный вариант реализации для калибровки, не утверждённый
пользователем коэффициент**; он повторяет базовый спрос stadium policy без бонуса поля.

Две выплаты дают в сумме ровно выручку; нечётная единица распределяется seeded draw
по IDs клубов/арены. Перестановка участников не меняет получателя. Восстановленный
результат проверяет спрос, выручку, draw и фактическую выплату остатка. Переполнение
BIGINT и bool вместо чисел отклоняются. Третьему клубу/арене выплата не создаётся.

До подключения нужно выбрать/забронировать арену, сохранить snapshot, убрать обычный
доход хозяина и бонус поля из runtime, записывать две ledger credits атомарно с
финальным результатом с ключами fixture+club. Повтор использует прежние snapshot,
остаток и ключи, rollback не должен оставлять одну из двух выплат. Сам калькулятор
никому не перечисляет деньги. Нужны проверки этих транзакций и игровой экран финала.

## Приёмка

Добавлены регрессии на результаты из чужой ветви, преждевременного чемпиона,
некорректный восстановленный граф, смешанные сезоны, неверного получателя остатка
и искусственно завышенную посещаемость. Общий сценарий для 1/2/3/4 комплектов
передаёт новое membership в кубок, проходит все 49 противостояний, проверяет
отсутствие двух матчей клуба в один кубковый день и разделяет доход финала.

Схема БД не изменена, новых миграций и тестовых БД нет. Проверка существующей
Goaletto development БД ограничена `alembic check`, без сброса игрового мира.
