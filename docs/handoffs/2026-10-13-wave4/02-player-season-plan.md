# B · Чистый план старения и завершения карьеры футболиста

Ты внешний разработчик Goaletto — Python-футбольного менеджера в Telegram.
Репозиторий: https://github.com/anry88/Goaletto (закрытый, лицензию не менять).
Работай только над указанным подпакетом и передай готовый код Codex для review.
Не запускай других агентов и не отправляй сообщения от имени пользователя.

Перед началом:
- Прочитай AGENTS.md, README.md, docs/game-rules.md, docs/match-clock.md,
  football-manager-bot-gdd.md и документы ниже. Архивный GDD v1 не источник правил.
- Получи актуальный origin/main и создай отдельную ветку codex/<имя-задания>.
  Запиши исходный SHA. Не продолжай старую агентскую/integration-ветку.
  Код на момент подготовки проверен на main 63812358; это справка,
  а не разрешение начинать новую ветку с устаревшего commit.
- Сначала проверь текущую реализацию: исторические статусы в документах/Linear
  могут отставать. Не реализуй повторно уже работающую функцию.

Общие границы:
- Только Python для приложения, Telegram, PostgreSQL. Без Mini App, JavaScript,
  нового публичного API, LLM в симуляции и новых игровых правил.
- Domain без aiogram/SQLAlchemy/сети/часов; время и seed передаются явно.
- Обычный матч: 30 тиков по 60 секунд, 3 игровых минуты на тик,
  перерыв 180 секунд, всего 33 реальные минуты плюс зафиксированные остановки.
- Изображения/портреты/каталоги/appearance IDs не менять и не генерировать.
- Не трогай файлы вне своего списка. Нужное изменение общей границы оформляй
  отдельным точным integration.patch и объясняй его. Исключения перечислены в задании.
- PostgreSQL владеет durable состоянием. Не подменяй его FSM/памятью процесса.
  Системные события и доставка не продлевают владение клубом.
- Не запускать настоящие polling/sender, не использовать Telegram-аккаунты,
  не трогать production/соседние сервисы, не сбрасывать рабочую БД.
  Новые локальные/CI тестовые БД и PostgreSQL services запрещены.
  PG-тесты можно написать; исполнение на единственной Goaletto DB выполняет Codex
  последовательно после сохранения мира. Отсутствие доступа не заменять SQLite.
- Не читать/копировать секреты в результат; не печатать токены, DSN, raw exceptions
  с credentials, тексты приватных сообщений. Используй fake transport/runner.
- Тексты игры RU/EN; без технических ID, версий, тиков и объявлений о твоих изменениях.

Сдача:
1. Commit/patch или PR, исходный SHA, список изменённых файлов.
2. Реальное поведение и границы подпакета; никаких обещаний готовности целого MVP.
3. Ruff check, ruff format --check, mypy и релевантный pytest. Для миграций —
   offline SQL upgrade/downgrade и пояснение схемы. Честно отдели passed от skipped.
4. Короткий воспроизводимый сценарий приёмки Codex и оставшиеся ограничения.
5. Не merge/push main и не закрывай Linear. Codex проведёт review, PG/native проверки,
   сведёт принятую работу в main и обновит задачи по фактически выполненному объёму.

## Задание

Связь с Linear: чистая расчётная часть AND-64/57, без durable rollover.
Ветка: codex/player-season-plan.

Результат: готовая чистая функция, которую Codex использует в общей транзакции
rollover. Сейчас domain.retirement.player_last_season уже реализует вероятность,
а domain.leagues.plan_season_movements — переходы клубов. Не дублируй эти функции.
Сезонного перехода player состояния пока нет; проверь это перед началом.

Прочитай docs/player-lifecycle.md, docs/staff-lifecycle.md, docs/bot-clubs.md,
domain/retirement.py, application/persons.py, application/world.py и модели
Person/Player/PersonSeasonEvent. Существующие models только читать.

Сделай новый domain/player_season_plan.py с immutable typed input/output:
- Вход содержит person_id, текущий завершённый сезон, следующий сезон, возраст,
  текущий status/last_season_id, явно переданную выборку и, при повторе,
  уже сохранённое решение/план перехода. Опиши точный публичный API в документе.
- Если завершившийся сезон был объявленным последним: retirement, возраст
  последнего сыгранного сезона сохранён, нового draw/активного сезона нет.
- Для оставшегося активного футболиста возраст следующего сезона +1; вызвать
  существующую player_last_season с утверждённой шкалой 5/10/20/35/55/80/100%.
  Положительное решение назначает весь следующий сезон последним; не retirement
  в момент объявления. Возраст38 всегда last season, active39 невозможен.
- Повтор с уже принятым решением не меняет outcome/policy/draw/возраст. Явно
  различай повторный вход с исходным состоянием и уже применённым состоянием;
  несовместимые person/season/receipt не должны маскироваться как успешный retry.
  Чистая функция не гарантирует транзакционную идемпотентность: покажи, какие
  ключи/receipt обязан сохранить и проверить вызывающий application-код.
- Retired повторно не стареет и не возвращается в активную карьеру. Last-season
  статус и season ref должны быть согласованы; не исправляй повреждённый ввод
  молча. Проверяй возраст, типы (bool не integer), draw bounds, различие сезонов.
- Выход — план изменения player-состояния и данные решения с policy version;
  без ORM, events/outbox, UUID генерации, random, часов, IO. Person/appearance
  identity передаётся неизменной; archived snapshots не переписываются.

Не добавляй рост/деградацию навыков, мораль, staff retirement/career lottery,
молодёжное пополнение, формы, портреты, market cancellation, записи в БД или
worker jobs. Для них нужна центральная транзакция либо ещё не утверждённые правила.
Не подключай функцию к игре самостоятельно. После review Codex отвечает за
сохранение receipt, блокировки, отмену аукционов и общий rollover.
