# Создание мира и календаря

Дополнение 2026-10-14: [календарь, кубки и переходы AND-118–128](calendar-cups-update-2026-10-14.md).
Четырёхдневный цикл заменяет прежние недельные даты; точные старты — в горизонте
10 дней. Лига назначения при переходе не ограничена комплектом.
Описание старого прототипа ниже сохраняется как состояние реализации.

Реализованы чистый план мира, подбор подходящих цельных внешностей, недельный календарь
и PostgreSQL use case `initialize_world`. CLI по умолчанию работает офлайн. Рабочая БД
не заполнена, HDC не менялся. Миграция `0003_world_seed` добавляет receipt и статус
jobs `held`, всего 25 таблиц. Проверки выполняются без подключения к БД.

## Офлайн-предпросмотр

```bash
python -m goaletto.application.world_cli \
  --key initial --seed 0 --first-kickoff 2026-10-17T18:00:00Z \
  --output work/initial-world-preview.json
```

После установки пакета доступна та же команда `goaletto-world`. Дата начала передаётся
явно: суббота 18:00 UTC. Дата примера не записана как глобальная настройка сервера.
Без `--apply` команда не создаёт Database/Settings, не читает `.env` и не подключается
к PostgreSQL. На stdout — краткий итог; JSON содержит все клубы, игроков, fixtures
и сроки задач. Это локальный снимок плана, без пользовательских событий.

Проверенный пример: 5 лиг, 50 клубов, 1000 футболистов, 1000 уникальных лиц,
450 матчей, 15302 held jobs. 102 игрока получили метку последнего сезона.
Среднее восьми основных навыков всех составов — 8.91875, spread между клубами — 0.
Используются подготовленные whole-v2 файлы; генерация изображений не нужна.

## Стартовая модель v1

В каждой лиге 10 клубов, все без владельцев. Общий шаблон — 4-4-2 и 20 футболистов:
GK×2, DL×2, DC×3, DR×2, ML×2, MC×3, MR×2, FC×4. Слоты 1–11 — основа, 12–20 —
постоянный порядок резерва с запасным GK. Это ёмкость хранения состава, не новое
правило количества матчевых замен. Нет оптимизации под tier, соперника или счёт.

Имена, небольшие вариации навыков и пенсионный draw воспроизводимы по seed.
UUID стабильны по key мира и слоту. Одинаковый key с изменённой конфигурацией нельзя
применить поверх прежнего мира. Разные комплекты получают разные club/person IDs.
Жребий 1–10 сохраняется до сезона для будущего разрешения равенства в таблице.

Профиль зависит только от позиции. Профильный навык полевого игрока — 12, GK — 14;
два остальных навыка получают компенсирующее +1/−1. Лидерство/лояльность 9–11,
форма 6, мораль 50, опыт 0, травм нет. Core sum и профильная сила XI одинаковы
у всех 50 клубов, без tier handicap. Core sum — контроль стартовой сопоставимости,
не окончательный игровой OVR; матчевые формулы/прогресс ещё требуют баланса.

Общий стартовый бюджет задаётся `--budget` целыми минимальными единицами.
По умолчанию 0: экономическая модель пока не реализована. Это параметр seed,
не утверждённая цена или платёжная единица. Персонал автоматически не создаётся:
размер и роли стартового кадрового пула ещё не заданы.

| Слоты | Возрасты по порядку |
|---|---|
| Основа 1–11 | 25, 24, 29, 31, 26, 23, 27, 28, 22, 30, 24 |
| Резерв 12–20 | 19, 21, 33, 35, 20, 32, 36, 18, 38 |

Возрастной шаблон одинаков для клубов и не определяется внешностью. Сначала строится
игровой план, потом сопоставляются identity/variants нужной возрастной группы.
Подготовленная стадия имеет приоритет; base portrait допустим, если изображённый
возраст лежит в той же визуальной группе. Несколько вариантов одной identity
не дают несколько лиц для разных людей. При недостатке свободных и подходящих
возрасту лиц операция прекращается, без подстановки чужого или неподходящего лица.
Частичного расширения хватает для первого seed; для дальнейшего старения ещё
потребуется пополнить отсутствующие стадии.

Чистая `player_last_season(age, draw)` реализует согласованные 5/10/20/35/55/80/100%
в 32–38, в 38 метка обязательна. Seed сохраняет один decision первого сезона и
отметку исходного возраста, без дополнительного +1 при создании. Пенсия, рынок,
тренировки и переход в staff здесь не выполняются. Статус last_season записан
в профиль: будущий рынок обязан проверять его под общим player/person lock.

## Календарь

Circle planner создаёт 18 туров: 9 парных туров и обратные встречи. Каждая пара
играет дома/в гостях, клуб — один раз за тур; у каждого 9 домашних и 9 гостевых.
На лигу 90 fixtures, на комплект 450. Даты еженедельно в UTC; DST влияет только
на локальное отображение. Календарь каждого комплекта независим.

Последний плановый матч заканчивается через 17 недель и 33 минуты после первого
kickoff. Затем две субботы без матчей лиги; следующий первый kickoff — через
20 недель от предыдущего первого. Создание следующего сезона и переходы выполняет
будущий rollover. При переносе/паузе runtime должен согласовать фактические границы,
а не завершать сезон по одному наступившему плановому timestamp.

На fixture подготовлены 34 задачи: reminder за 5 минут, lock за минуту, старт,
30 минутных тиков и начало второго тайма в 18:00. Тик 15 — 15:00, тик 16 — 19:00,
тик 30 — 33:00. Ещё две задачи на season: open перед reminder и rollover после
последнего планового финального тика. Dedupe keys, UUID и deadlines стабильны
по season/fixture/stage/tick.

Все календарные jobs сохраняются **held**. Текущий worker берёт только pending и
умеет system.ping; match jobs не включаются. AND-52 добавит handlers/recovery,
AND-68 — sender. Затем поддерживаемые held jobs можно переводить в pending,
с учётом актуального календаря и пропущенных окон; не активировать старые даты залпом.
В этой работе нет отправленных уведомлений или проведённых матчей.

## Запись в игровую БД

Use case готов для подключения к существующей игровой БД. Здесь команда записи
не запускалась. После миграций игрового проекта оператор явно использует:

```bash
goaletto-world --key initial --seed 0 \
  --first-kickoff 2026-10-17T18:00:00Z --apply
```

Подключение — GOALETTO_DATABASE_URL; вывод DSN/токенов запрещён. При первом создании
время должно предшествовать season open/reminder. Повтор после начала матчей
возвращает прежний receipt без сброса мира.

Одна caller-owned транзакция:

1. Общий `pg_advisory_xact_lock(710045001)` с публикацией каталога/назначением лиц.
2. Receipt по key: тот же config hash возвращает прежние IDs, другой hash — ошибка.
   Retry не перечитывает каталог и не обнуляет состояние.
3. Если set есть без receipt — отказ, без автоматического удаления/починки.
4. Публикация каталога, подбор разных лиц внутри первого состава; банк повторно доступен другим комплектам.
5. Set/5 leagues/50 clubs/season, 1000 persons/profiles, 2000 age/decision events,
   lineup/slots, memberships/standings, fixtures и held jobs.
6. Receipt последним, затем caller commit. При ошибке вся транзакция откатывается.
   Пакеты по 500 записей укладываются в bind parameter limit asyncpg.

Receipt append-only и независим от будущего claim/трансферов/переходов: финансы,
лица, составы и владение при retry не сбрасываются. Решение 2026-10-13 позволяет
следующему комплекту использовать тот же каталог 1 000 иллюстраций. Собственные
person IDs и истории различаются; закреплённое лицо не меняется.

Unit-проверки подтверждают популяцию/баланс/позиции, лица, календарь, пенсионные
draw и ветви receipt. SQL-recording test исполняет application и компилирует batches,
без БД или подключения; он не доказывает реальные PG race/rollback/lock semantics.
Исполнение миграций и seed на PostgreSQL пока не проверено по решению пользователя.
Downgrade 0003 удаляет held calendar:v1 jobs и receipt, сохраняя население; повтор seed
после него требует reconciliation. Наличие иных held jobs блокирует downgrade,
чтобы не активировать/удалить их молча. Это технический откат, не reset мира.

[возраст](player-lifecycle.md), [задачи](linear-backlog.md).
