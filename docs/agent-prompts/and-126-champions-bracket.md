API принимает явно frozen ChampionsGroup, отдельный tournament_id UUID и seed.
Tournament ID выбирает orchestration: не используй произвольный сезон одного
участника как сезон межкомплектного турнира. Квалификация уже зафиксирована в
группе: не отбирай top8 повторно, не меняй qualifying tier/season по текущему
положению клуба и не выдумывай прошлую таблицу для первого сезона.

Участников N=8/16/32/64/128/256/512. Все начинают с первого раунда, без staged
entry кубка 50 клубов и без bye. Первый жребий seeded, независим от порядка
participants/group input; сортировка UUID — только база перед shuffle, не пары.
Далее победители продвигаются по зафиксированным ссылкам, без нового случайного
жребия при каждом результате или retry. Точные пары и policy должны быть
пригодны для будущего persisted snapshot.

Результат: небольшой immutable graph с устойчивыми tie IDs в namespace
tournament/group/policy/round/index, слотами club ID или winner(tie ID), номером
раунда и структурными champions cycles. Можно переиспользовать CupSlot и его
конструкторы, если их контракт подходит; CupTie/CupLeg ограничены фиксированными
раундами другого кубка — не меняй их ради нового соревнования. Не копируй весь
модуль cup_bracket.py и не строй второй матчевый движок: нужны лишь данные
сетки, компактное построение по раундам и необходимая проверка/разрешение слотов.

Каждая пара до финала играет два матча с обменом поля. Раунд r занимает циклы
2r-1 и 2r; финал при R=log2(N) — один нейтральный матч в цикле 2R-1.
Итого N-1 противостояний, 2N-3 матчей, 2*log2(N)-1 матчевых дней (5..17).
Фаза — день 2 четырёхдневного цикла. Остальные cycles D+1..18 свободны;
18-й всегда резерв, без фиктивных игр. Никаких фактических UTC kickoff/jobs здесь.

Предоставь минимальные pure readers: раскрытие legs, получение финала,
разрешение известного слота и possible club IDs в будущем слоте после вылетов.
Принимаются только окончательные tie winners от существующего knockout API;
ничья одного матча не считается победителем. Все публичные readers проверяют
результаты: чужой/не участвующий в этой паре winner, пропущенные предшественники,
проигравший в следующей ветке и противоречие — ошибки. Финального победителя
нельзя объявить по одной записи финала без предшествующих результатов.
После вылета клуб исчезает из зависимых будущих ветвей, другая ветвь сохраняется.

Проверяй восстановленный graph: frozen участники группы входят каждый один раз,
нет чужих/потерянных клубов, циклов, повторного использования feeder tie в двух
местах, одинаковых соперников, неверных раундов/дней и лишнего/пропавшего финала.
Стабильность IDs/replay не должна зависеть от wall-clock или порядка словаря.
Не дублируй aggregate/ET/pens, минуты/энергию/прогресс, arena/ledger или bootstrap.

Последнее игровое правило: все матчи влияют на форму и развитие; товарищеские
дают меньший прогресс. Эта сетка не начисляет рост сама и не вводит запрет
кубкового прогресса. Его подключает Codex по AND-130 в общем runtime.

Проверки: все семь размеров N, counts/days/home-away/neutral final,
полный проход до чемпиона, стабильный seed и input permutation, unknown slots
до и после вылета, повреждённые graphs/results, отсутствие матчей свободных cycles.
Хотя бы один пример получения winners через domain.knockout, включая ET/pens,
и передача двух известных финалистов в существующий neutral_final калькулятор;
реальный match engine или новый генератор голов для этого не нужен.
