# Вход первых игроков и проверяемые отчёты · AND-75/76/79

Игровой `/start` принимает source-код и сохраняет неизменный первый источник.
Проверен настоящий Dispatcher с PostgreSQL и fake Telegram: известная кампания,
неизвестный код, прямой вход, повтор Update, internal account, preview и прямой
claim без preview, ручное сохранение состава. Невалидный payload не хранится;
корректные start-метки автоматически распознаются без предварительной регистрации
([правила](analytics/acquisition.md)).
Публичные агрегаты не содержат Telegram ID, менеджерских refs или текста сообщений.

## Ошибки и продолжение

Вход и редактор состава фиксируют конечные категории `invalid_input`,
`club_unavailable`, `permission_denied`, `lineup_invalid`, `stale_action`.
Ошибочная бизнес-транзакция сначала откатывается; наблюдение сохраняется отдельно.
Для устаревшей ревизии/владения показывается актуальный состав, для остальных
ошибок — кнопки выбора клуба или открытия состава/клуба. RU/EN поддержаны.

`action_rejected` не продлевает сессию или владение. Подтверждение
`help_delivered` / `club_offer_delivered` появляется **после** успешного Telegram
send/edit, вне транзакции. У direct response используется существующий
`operation_id` с зарезервированным effect 31001 и ограниченным target; у outbox
сохраняется прежний `outbox_id`. Новый JSON payload/таблица/очередь не нужны.
Отсутствие подтверждения означает неизвестный исход, включая crash после send.
Подтверждение не доказывает прочтение и не создаёт retention.

Transport retry сохранённой команды показывает актуальное состояние, без второго
сохранения или ложного rejection. Новое нажатие старой кнопки — отдельный stale
request. Наблюдения сериализуются manager lock, retry/rollback проверены на PG.

Recovery — успешный **claim** после ошибки входа или **ручной save** после ошибки
состава в `[error_at, error_at + 30 минут)`, того же менеджера и, когда указан,
того же периода владения. Открыть экран, получить подсказку или фоновое сообщение
недостаточно. Новое владение тем же клубом не восстанавливает старую операцию.
Знаменатель созревает через 30 минут; строки считают rejected requests, поле
`managers` отдельно показывает затронутых людей. Несколько ошибок могут иметь
одно успешное продолжение. Это наблюдаемое продолжение, не доказательство причины
ошибки или ухода. До установки этого инструментирования ошибки задним числом
не восстанавливаются; отсутствие rejection не доказывает отсутствие проблем.

## Операторские команды

Через `python -m goaletto.application.analytics_reports_cli`:

- `last-steps`: последний подтверждённый user effect; source/campaign, язык,
  UTC-неделя входа и маршрут `preview_claim` / `direct_claim` / `unclaimed`.
  Отдельно показано принятие Telegram экрана с предложениями.
- `recovery`: ошибки по причине/экрану/целевому действию, зрелый N, waiting,
  подтверждённая/неподтверждённая помощь и успешное продолжение n.
- `match-opportunities`: первое участие и возврат ко второму, зрелые n/N,
  waiting, interrupted, no_calendar, coverage, unavailable, unsupported,
  unknown_late. При N=0 rate=null. Второй N включает только участников первого.

Каждая команда принимает `--cohort-from <UTC ISO> --at <UTC ISO>`;
без `--apply` выводит preview и не подключается к БД. С `--apply` работает в
server READ ONLY REPEATABLE READ snapshot. Существуют также `entry-funnel`,
`retention`, `delivery` и source report в `campaign_cli`.

Матчевые возможности читают полный календарь планов, а не только объявленные
десять дней. Необъявленная дата даёт waiting без выдуманного времени начала.
Порядок учитывает actual start после переноса; окно участия использует actual
start−24ч / actual finish+24ч. Владение требуется до lineup lock и до конца окна;
claim после lock пропускает матч. Просроченный lease учитывается даже до expiry job.
Проверяется полнота 90 league plans/fixtures в исторической лиге сезона и наличие
финального receipt на момент отчёта. Кубки/товарищеские не увеличивают лиговый KPI;
их явные действия остаются видны в last-steps. Более ранний незавершённый матч
блокирует перескакивание к следующему зрелому. Abandoned не трактуется как
обычная завершённая возможность.

`recorded_at > T` не даёт участие; поздний T пересчитывает окно. Первый claim до
начала наблюдения даёт coverage, а не ложную первую историческую возможность.
Internal/opt-out исключены; cohort обрезается по coverage и retention с явной
меткой. SQL выдаёт агрегаты, не загружает весь архив в Python и не делает N+1.
Исторические изменения расписания/lease без отдельного журнала не реконструируются:
используется сохранённое текущее расписание и фактические результаты.

Это готовит измерение закрытого теста. AND-77 теперь имеет отдельную
[техническую цепочку и latency](runtime-observation.md); AND-119 подключает
[общий календарь новых комплектов](world-reserve.md). AND-78 подключает
[внутренние опросы](feedback.md), AND-82 — [локальный gate](analytics/launch-gate.md).
AND-80 (Grafana), сверка реальных доступов и HDC deployment остаются впереди.
Реального polling/отправок/привлечения эта приёмка не запускает.
