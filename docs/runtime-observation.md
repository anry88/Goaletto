# Техническая цепочка матчей · AND-77/69

Игровое участие считается по явным действиям и матчевым возможностям, как
описано в [launch-measurement.md](launch-measurement.md). Технические попытки
хранятся отдельно и включают internal/test аккаунты. Ни ticks, ни восстановление,
ни доставка, ни эти замеры не создают user activity, сессии или продление владения.

## Запрос менеджера

`runtime_requests` — отдельная попытка обработки `/match`, `lv:*`, `hx:*`, `hr:*`.
Кнопка подтверждается прежним `answerCallbackQuery` до записи замеров.
`received_at` означает начало наблюдаемой части обработчика после ACK/проверки
типа сообщения, а не время нажатия на устройстве или получение Update Telegram.
Задержка polling/ACK/предшествующего language middleware сюда не входит.

Операционный UUID совпадает с игровым: Telegram update для `/match`, callback
UUID для кнопок. Новая доставка того же callback создаёт новую попытку, но
ссылается на ту же accepted command. FK `fixture_id` / `command_id` позволяют
сопоставить запрос, фактическое применение команды, tick/stage и outbox этого
матча. Ни callback payload, ни Telegram/user/chat ID, ни текст экрана не сохраняются.

`business_outcome=committed` / `committed_at` фиксируются **после возвращения
настоящего commit**. Отказ бизнес-правил — rejected; потеря связи во время commit
может остаться unknown. Если процесс упал между commit и записью наблюдения,
команда остаётся в игровом журнале, а время commit не выдумывается. Retry читает
её обычным способом. Ошибка сохранения замеров не отменяет игру/ответ; лог содержит
только класс ошибки. Запись замеров ограничена одной секундой; после первой
ошибки остальные записи этой попытки отключаются. Отсутствие наблюдения не
доказывает отсутствие запроса.

Чтение данных и игровой commit завершаются перед форматированием экрана.
Отдельные `render_started_at` / `rendered_at` измеряют чистое форматирование;
`network_started_at` — сохранённое намерение вызвать Telegram, не доказательство
поступления запроса. `accepted` появляется после успешного ответа Telegram;
явный отказ API — rejected, timeout/неожиданная сетевая ошибка — unknown.
Падение после send intent без finish остаётся неизвестным, даже после restart.
Это наблюдение ответа целиком: при нескольких Telegram-вызовах ошибка последнего
может оставить консервативный unknown. Прочтение экрана не измеряется.

Интервал `request_telegram` начинается с durable send intent и включает его commit
перед вызовом API. У sender `delivery_telegram` также включает commit preflight.
Это наблюдаемые границы всего этапа отправки, не изолированное время сети Telegram.

## Worker и очередь

Существующие `operation_attempts` дают длительность обработки и опоздание
относительно конкретного `due_at`. Это времена обработки, а не наблюдение возврата
COMMIT. Только обычные `match.*` входят в эти перцентили; исторический
`world.catch_up:*` исключён, чтобы подготовка бот-комплекта не изображала сбой live.

Новые outbox строки получают физический `enqueued_at` на INSERT. Старые строки
остаются NULL: миграция не достраивает историю. В `outbox_delivery_attempts`
`available_at` замораживает due_at каждой попытки **до** изменения backoff.
Ожидание очереди считается от max(enqueued_at, available_at) до claim, без ожидания
будущего матча/напоминания и без запланированного retry backoff. От enqueue до claim
входит также остаток транзакции производителя; это верхняя оценка чистой очереди.

Sender проверяет получателя, выходит из транзакции, форматирует текст, затем
снова проверяет актуальность/ownership/lease и сохраняет send intent. Только после
этого вызывает Telegram. DB-транзакция не держится ни при render, ни при сети.
При crash во время render network intent отсутствует; после него результат
неизвестен. Перед повтором остаются прежние lease/token/attempt fences. Явная ошибка
render завершает попытку без вызова сети. Сохраняются RU/EN и local kickoff display.

## Операторский отчёт

```bash
python -m goaletto.application.runtime_observation_cli \
  --since 2026-10-18T00:00:00Z --at 2026-10-19T00:00:00Z
# Добавить --apply для READ ONLY REPEATABLE READ существующей БД.
```

Preview не загружает настройки и не подключается. Вывод — только конечные названия
метрик, observations/measured/unknown, p50/p95 секунд и состояния запросов. При
отсутствии замеров перцентили NULL, не ноль. Нет идентификаторов и содержимого
сообщений. SQL ограничивает окно индексами; все агрегаты читаются одним snapshot.
Поздние finish/commit за `--at` не выдаются за известный результат в этом окне.

`command_wait_for_tick` показывается отдельно: ожидание следующего разрешённого
тика — игровое расписание, **не техническая latency**. Оператор не складывает его
с worker processing или request render и не делает из этого вывод об уходе игрока.
Отчёт также показывает последний текущий scan reconciliation с его собственным
временем, количеством восстановлений, конфликтов и повреждений; это оперативный
снимок, а не реконструкция старых сканов на произвольную дату.

Измеренные здесь секунды не являются нагрузочным SLA production. Числовые ограничения
запуска остаются в AND-71; системный monitoring/reboot/backup — AND-70/72.

## Безопасный reconciliation

Game-enabled worker при старте ставит одно durable `runtime.reconcile` и повторяет
scan каждые 30 секунд, максимум 50 live-матчей за транзакцию. UUID-cursor обходит
следующую пачку, затем возвращается к началу. Allocation gate сериализует scan
с claim, worker и rollover. Paused fixtures, выключенные календари и ещё
готовящиеся WorldAdmission исключены.

Проверяются JSON checkpoint, tick/phase, next_due_at и совпадение hash с сохранённым
immutable tick/stage. Восстанавливается только **отсутствующее ближайшее** задание
по этому checkpoint — tick, halftime, ET либо penalty. Retry/rollback/параллельный
worker не создают вторую копию. Сам scan не считает матч и не меняет его clock.
Просроченный восстановленный job проходит обычный [live recovery](live-recovery.md):
сначала выдаёт полное окно решения, затем один переход в срок.

Если job есть, но held/failed/done, срок расходится или checkpoint не подтверждён,
автоматического сброса нет. В payload scan сохраняются `corrupt` / `conflicts`;
read-only диагностика продолжает показывать повреждение/потерянную границу. Оператор
разбирает причину. Финансы/settlement/results не пересчитываются по догадке,
отсутствующие legacy receipts не создаются, paused матч сам не возобновляется.

Результат/ledger/outbox создаются исходными атомарными обработчиками. После потери
БД надо восстановить соединение и обычный worker, затем проверить diagnostics и
этот отчёт. Не переводить failed job в done и не помечать неизвестную отправку sent.
Локальные crash/rollback тесты не заменяют production reboot/DB-disconnect drill; эта
операторская часть AND-69 остаётся до production smoke.
