# Запас клубов и общий календарь новых комплектов · AND-47/119

Решение пользователя 2026-10-18: заранее иметь минимум 10 свободных клубов
пятой лиги. Новый комплект входит в общий календарь; его прошедшие матчи
рассчитываются между ботами **до выдачи** клуба человеку.

## Выдача и запас

`/start`, список, preview и claim используют только готовые комплекты.
Регистрация не создаёт мир и не рассчитывает матчи. При остатке 10 мест
или меньше она только ставит одно долговечное задание `world.reserve`.
Worker с включённой игрой также ставит его при запуске; затем оно проверяет
запас каждую минуту. Цель пополнения — 10–20 готовых мест: один новый комплект
добавляет десять клубов tier 5. Это порог пополнения, а не запрет выдать последние
готовые клубы. Если фон остановлен/пришёл большой всплеск регистраций, уже готовые
места остаются доступны; пустой запас даёт кнопку обновления, без долгой операции
в запросе человека. Перед открытием трафика нужно дождаться пополнения:
больше 10 готовых мест (до 20), без незавершённой подготовки. При уже занятых
клубах целого нового комплекта может хватить, например, для 19 мест.

Общий allocation lock сериализует создание комплектов/claim/rollover.
Повторные и параллельные запросы не создают лишние комплекты; уже готовые
места и один готовящийся комплект учитываются перед новой генерацией.
Существующий банк лиц переиспользуется с least-used назначением; личности,
история и уже назначенные лица сохраняются, новых картинок не требуется.
Старые деньги/состав/статистика при claim не сбрасываются.

`entry_opened` — операционный receipt первого принятия Update, отдельный от
аналитики. Повтор старого `/start` после claim, opt-out или удаления аналитики
не становится новым игровым действием и не продлевает владение. Новый Update
владельца по-прежнему является явным действием.

## Подготовка нового комплекта

Worker выбирает общий последний season cohort под allocation lock и копирует
его epoch/границу/первую лиговую дату и номер общего сезона. Предыдущие
сезоны/таблицы новому комплекту не придумываются, в том числе для отбора чемпионов. Если
общий новый сезон ещё впереди, матчи прошлого сезона новому комплекту не нужны.
Старые несовместимые операторские/dev-календари не смешиваются: reserve job
откладывается до их исправления. Legacy-синхронизация не добавлялась.

`WorldAdmission` сохраняет настоящий момент запроса, источник календаря,
начало воспроизведения и момент допуска. Создание мира и задания — одна транзакция.
Контракты, зарплаты, спонсор и стартовый ledger нового виртуального мира начинают
действовать с начала его игрового календаря; receipt создания хранит реальную дату.
Старые клубы и их pending jobs не перематываются.

`world.catch_up` исполняет обычные durable season/calendar/finance/match jobs
по их историческим дедлайнам, максимум 40 переходов за одну транзакцию.
Получаются настоящие ticks/checkpoints, минуты, голы, standings, кубковые пары,
ET/пенальти, практика, восстановление и финансовые receipts. После каждого batch
прогресс коммитится; сбой откатывает только текущий batch. Следующий worker
продолжает по сохранённым jobs, без второго результата/списания или нового draw.
Точное время будущих матчей по-прежнему фиксируется только на десять дней.
Системные journey/result receipts записывают реальный момент расчёта отдельно
от исторического времени матча; replay attempts имеют отдельный stage prefix.
Исторические события до фактического начала аналитики не создают задним числом
покрытие наблюдения: их результаты сохраняются, а продуктовые события пропускаются.

Обычный worker пропускает jobs готовящегося мира. Исторический режим допускается
только для pending WorldAdmission; после допуска он запрещён. Подготовленный мир
до ready_at отсутствует в offers/preview/claim, включая старые прямые callbacks.
PostgreSQL запрещает выдачу клуба/создание ownership до ready_at, и запрещает
создавать historical admission для комплекта, который уже был у человека.

Допуск происходит после обработки всех задач до текущего момента, без failed jobs
и пропущенных прошлых объявленных участников. Текущий матч может оставаться live:
его прошедшие ticks уже рассчитаны, будущие идут в реальном времени. Получивший
такой клуб менеджер не переписывает заблокированный состав. Rollover никогда
не выполняется внутри исторического режима: он ждёт общего cohort.

## Проверка запаса

```bash
python -m goaletto.application.world_capacity_cli
python -m goaletto.application.world_capacity_cli --apply
```

Без `--apply` подключения нет. С ним — READ ONLY REPEATABLE READ и только
агрегаты ready_free_tier5 / preparing_sets / reserve_healthy /
prewarmed_for_launch. Секреты и Telegram ID не выводятся. Включённый обычный
worker выполняет подготовку; CLI сам ничего не генерирует и не отправляет.
При недоступности каталога/повреждённом состоянии смотрите failed job и diagnostics;
не допускайте комплект ручным изменением ready_at и не считайте его запасом.

## Общий переход

Все последние сезоны с одинаковыми epoch/end образуют обязательную когорту.
Поздний последний матч, незавершённый кубок или подготовка нового комплекта
задерживают **всю** когорту. Первый отработавший job не может выбрать отдельный
allocation. После готовности остаются существующие единый persisted draw,
атомарные membership/возраст/спонсоры/календарь/отбор чемпионов и безопасный retry.
Незавершённость не компенсируется фиктивным результатом или повторным старением.

Новый комплект получает текущий общий номер сезона. При чтении истории всё
равно учитывается календарная дата, а не наибольший локальный номер: это сохраняет
корректность для ранее созданных комплектов с разной нумерацией.

## Приёмка · 2026-10-18

- Полный новый бот-комплект до допуска: 450 настоящих результатов лиги,
  97 кубковых результатов и 49 решённых пар, ticks/ET/пенальти, без failed jobs.
  Исходный комплект с владельцем не перематывается.
- PostgreSQL: параллельное пополнение создаёт один комплект; pending-клуб
  нельзя получить через callback или SQL; сбой batch откатывается, продолжение
  не дублирует результаты. Новый комплект копирует общий сезон №7 без создания
  шести выдуманных прошлых лет.
- Завершённый полный сезон ждёт незавершённого совместимого соседа, без
  частичного rollover. Атомарность/draw/membership проверены для 2/3/4 комплектов;
  несовместимые календари остаются отдельными. Сценарий перехода из локального
  сезона №7 в №2 проверяет таблицу, календарь, академию, рынок и товарищеские.
- Финальный профиль: 18 PostgreSQL сценариев; отдельно 2 сценария аналитики
  при наличии/отсутствии первого `/start`. Повтор старого Update не продлевает
  ownership, новый Update продлевает; Dispatcher и match-practice regression проходят.
- 1092 unit/offline passed; Ruff/format (501 файл), mypy (180 модулей).
  SQL render head и execution 0039→0040→0039→0040, alembic check.
  Downgrade отказывается удалять admission/entry history.
- Все DB-прогоны последовательные на единственной Goaletto `127.0.0.1:5433`.
  Исходный мир восстановлен и проверен по fingerprint 72 таблиц; новых БД нет.

Polling, Telegram delivery и deployment не запускались. Фоновое пополнение
включится вместе с обычным game-enabled worker; перед открытием трафика
оператор проверяет готовый запас командой выше. Прогон тестового catch-up
не означает, что исходный восстановленный мир уже прогрет для запуска.
